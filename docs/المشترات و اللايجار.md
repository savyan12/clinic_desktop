# Implement Admin Module: Purchases & Rent

Implement a new admin-only section in the existing clinic management desktop application named **"المشتريات والإيجار" (Purchases & Rent)**.

The requirements below are based on the current project's architecture and analysis. Before implementation, inspect the existing Rust/Tauri backend, Vue frontend, database schema, authorization system, audit logging, reporting system, and export functionality.

The goal is to integrate this feature naturally into the existing application rather than introduce a separate or unnecessarily complicated system.

## 1. Scope and Business Rules

This is a simple administrative expense-recording module.

It records actual expenses paid by the clinic, specifically:

- Purchases.
- Building rent.

This module is NOT an inventory management system or a supplier management system.

Do not implement:

- Inventory or stock management.
- Supplier directories or supplier accounts.
- Supplier debts or outstanding purchase installments.
- Recurring contracts or automatic recurring expenses.
- Attachments or document uploads.
- Profit and loss reporting.
- Future or unpaid expense obligations.

Only record expenses that have actually been paid.

## 2. Expense Record Structure

Each expense record must contain:

- `type`: Purchase or Rent.
- `description`: Expense description.
- `recipient`: Supplier or landlord name, stored as free text.
- `payment_date`: Actual payment date.
- `amount`: Amount actually paid.
- `payment_method`: Cash or Bank Transfer.
- `reference_number`: Optional invoice or payment reference.
- `rent_period`: Optional rental month or period. Required when the type is Rent.
- `notes`: Optional notes.
- `created_by`: User who registered the expense.
- `created_at`: Record creation timestamp.
- `updated_at`: Last modification timestamp, where applicable.
- `status`: Active or Cancelled.

Use the existing database conventions and appropriate decimal precision for financial amounts.

Do not introduce unnecessary fields or relationships.

## 3. Admin Interface

Add a new navigation item named:

**المشتريات والإيجار**

The page should follow the application's existing design system, layout, Arabic RTL conventions, colors, typography, and interaction patterns.

The page must contain:

### Summary Cards

Display:

- Total Purchases.
- Total Rent.
- Total Expenses.

Only active records should contribute to these totals.

### Expense Table

Display the registered expense records with useful information, including:

- Payment date.
- Type.
- Description.
- Recipient.
- Reference number.
- Payment method.
- Amount.
- Status.

Provide:

- Search.
- Date filters.
- Expense type filter.
- Payment method filter.
- Status filter.
- Add new expense.
- Edit/correct an existing expense.
- Cancel an expense.

### Adding an Expense

Provide a clear form for creating a new expense.

When the user selects Rent, display the rental period field and make it required.

When the user selects Purchase, hide the rental period field and do not require it.

Use the application's existing form validation and modal/drawer patterns.

### Correcting an Expense

Allow authorized administrators to correct an existing record.

A correction must require a reason.

Record the correction in the audit log, including:

- Record ID.
- User performing the correction.
- Timestamp.
- Correction reason.
- Previous values.
- New values.

Corrections must not silently overwrite the historical audit trail.

### Cancelling an Expense

Allow administrators to cancel an existing expense.

Cancellation must require a reason.

Do not physically delete the database record.

Preserve its original information and cancellation history.

Cancelled records must:

- Remain visible in the records table when the relevant status filter is selected.
- Be clearly marked as cancelled.
- Be excluded from all active expense totals and report totals.
- Be excluded from active expense calculations.

Do not allow a cancelled record to affect financial summaries.

## 4. Permissions and Audit Logging

This section is exclusively for administrators.

Enforce authorization in the Rust backend, not only by hiding navigation items in Vue.

All operations must be audited:

- Expense creation.
- Expense correction.
- Expense cancellation.

Reuse the existing audit logging mechanism and conventions.

Do not create a parallel audit system if the application already provides one.

## 5. Database and Financial Integration

Create a dedicated database table for these expenses.

These records must remain separate from patient receipts and the existing patient financial ledger.

Important rules:

- Purchases and rent are actual cash outflows.
- They must never be recorded as patient payments.
- They must never modify patient wallet balances.
- They must never modify patient debts.
- They must never affect doctor commissions or payouts.
- The existing collections report must remain dedicated to incoming money.
- Cancelled expenses must not contribute to totals.

Inspect the current database architecture and implement the new table, indexes, migrations, and relationships using the project's existing conventions.

Ensure the current backup and restore mechanism automatically includes the new table's data. Do not create a separate backup mechanism.

The report must be integrated into the existing Reports page and follow its current design and functionality.

Display:

### Filters

Support the same relevant filters as the main section:

- Date range.
- Expense type.
- Payment method.

### Export and Printing

Support:

- On-screen report display.
- Printing.
- PDF export.
- Excel export.

Reuse the existing report export and printing mechanisms.

Ensure exported files contain the same filtered records and correct summary totals shown on screen.

Do not implement a separate export architecture.

## 7. Implementation Requirements

Before writing code:

1. Inspect the existing project architecture.
2. Identify the current admin authorization mechanism.
3. Identify the existing audit logging implementation.
4. Inspect the reporting and PDF/Excel export mechanisms.
5. Inspect the current database migration and backup/restore mechanisms.
6. Identify the most appropriate integration points.

Then implement the feature using the existing conventions.

Keep the implementation straightforward and maintainable.

Do not introduce unnecessary abstractions, dependencies, or architectural complexity.

Do not modify unrelated modules.

Do not modify the Laravel backend.

Preserve the existing incoming-payment and patient financial workflows.

## 8. Testing and Acceptance Criteria

Verify the following scenarios:

1. An administrator can create a Purchase expense.
2. An administrator can create a Rent expense with a required rental period.
3. A Rent expense cannot be saved without its rental period.
4. A Purchase expense does not require a rental period.
5. Cash and Bank Transfer payment methods work correctly.
6. Non-admin users cannot access the module or its backend operations.
7. Expense corrections require a reason and generate complete audit history.
8. Expense cancellations require a reason and preserve the original record.
9. Cancelled records are excluded from all expense totals.
10. Search and all filters return correct results.
11. Report totals match the underlying filtered active records.
12. PDF and Excel exports match the displayed report.
13. Existing patient collections and financial reports remain unchanged.
14. Backup and restore correctly preserve the new expense records.

Run the relevant tests and build checks.

Do not mark the feature as complete if important scenarios remain untested.

## Expected Result

A clean, professional, admin-only Purchases & Rent module integrated into the existing clinic management system.

It should provide accurate expense recording, correction and cancellation history, useful summaries, and fully integrated reporting without introducing inventory management, supplier debts, recurring contracts, or unnecessary financial complexity.
